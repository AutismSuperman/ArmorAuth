# ArmorAuth 操作手册

本文描述 ArmorAuth 运行后的常见管理和运营流程，关注系统上线后的操作员日常。首次了解产品使用流程时，建议先阅读 [基础使用](basic-usage.zh-CN.md)。

## 操作角色

| 角色 | 职责 |
| --- | --- |
| 平台管理员 | 部署、数据库、密钥、备份、监控 |
| 身份管理员 | 用户、组织、身份源、登录策略 |
| 应用管理员 | OAuth/OIDC 应用、Scope、Redirect URI、应用 MFA 策略 |
| 安全审计员 | 审计、Token 活动、Webhook 投递、策略验证 |

## 管理菜单与功能链路

| 菜单 | 主要任务 | 依赖关系 | 常见风险 |
| --- | --- | --- | --- |
| 首页 | 查看系统入口、关键统计和快速导航 | 服务端、管理 API、种子数据 | 首页只做导航和概览，不作为审计依据 |
| 应用列表 | 创建 OAuth2/OIDC Client、维护回调地址、认证方式、Token 设置、端点详情 | 租户、Scope、JWK、登录策略 | Redirect URI 误配、secret 泄露、公共客户端误用 secret |
| Scope 管理 | 定义应用可申请的授权范围和展示文案 | 应用、授权确认页 | Scope 过大或文案不可读 |
| OAuth 用户 | 搜索用户、查看联系方式验证状态、锁定/解锁、重置密码、角色维护 | 角色、组织、密码策略、审计 | 直接删除用户导致审计和绑定关系丢失 |
| 组织管理 | 维护租户内组织树和成员角色 | 租户、用户、Token claims | 把组织当成租户使用，导致隔离边界不清 |
| 租户管理 | 创建租户、品牌信息、状态、租户路径 | 应用、组织、issuer | 上线后修改租户编码会影响 URL 和集成方 |
| 登录策略 | 管理应用或角色触发的 MFA 要求 | 应用、角色、账号 MFA 因子 | 强制 MFA 前没有恢复流程 |
| 会话管理 | 查看活跃 session，必要时强制下线 | Spring Session、用户登录状态 | 单机 SessionRegistry 不能代表所有节点，HA 需 Redis session |
| Secret 保护 | 对身份源、Webhook、TOTP、JWK 私钥等密文做 rekey | crypto key、数据库备份 | 旧 key 未保留导致历史密文无法解密 |
| JWK 密钥 | 查看、轮换、废弃和删除非 active 签名密钥 | OAuth2/OIDC Token、JWKS 缓存 | 过早删除旧 key 造成依赖方无法验签 |
| 身份源 | 配置 OIDC/OAuth2、SAML、LDAP/AD、登录页展示和同步 | 外部 IdP、属性映射、本地用户 | subject 规则变化或邮箱匹配误绑定 |
| 外部账号绑定 | 查看和删除本地用户与外部身份的绑定 | 身份源、本地用户 | 删除绑定不是删除用户，需要单独处理生命周期 |
| 监控与审计 | 查看审计、Token 统计、异常登录和操作记录 | 审计事件、Token 事件 | 未建立巡检节奏时问题发现滞后 |
| Webhook | 将登录、Token、管理变更等事件投递到外部系统 | 审计事件、目标服务、签名 secret | 接收方不校验签名或事件订阅过宽 |

完整链路说明见 [功能链路总览](feature-flows.zh-CN.md)。

## 初始检查

首次部署后建议完成：

1. 确认公开 issuer URL 稳定且使用 HTTPS。
2. 替换开发管理员凭据。
3. 配置加密 key 和备份存储。
4. 确认 JWK 表已生成并纳入备份。
5. 检查默认应用、Scope、角色、权限和登录策略。
6. 确认管理操作会记录审计日志。

## 首次环境常用流程

新环境建议按这个顺序操作：

1. 确认或创建默认租户。
2. 只有当组织会影响授权、报表或管理边界时，再创建组织。
3. 创建第一个 OAuth2/OIDC 应用并验证 redirect URI。
4. 创建测试用户，按需验证邮箱和手机号，并分配角色。
5. 使用样例或接入应用测试托管登录和 Token 签发。
6. 为管理员和敏感应用开启 MFA。
7. 测试完成后查看会话、审计日志和 Token 统计。

本地开发种子数据应与共享环境隔离。

## 应用管理

应用代表 OAuth2/OIDC Client。

创建应用时需要确认：

- 为客户端类型选择正确的 grant type。
- 只登记可信 redirect URI。
- 浏览器和移动端客户端启用 PKCE。
- 只有能保护密钥的客户端才使用 confidential client 认证。
- Scope 控制在最小必要范围。
- 判断是否需要用户授权确认。
- 判断是否需要应用级 MFA。

运营注意事项：

- Client secret 只在创建或轮换时返回明文。
- 轮换 Client secret 需要与接入应用负责人协调。
- 调查或回滚可能发生时，优先禁用应用，而不是直接删除。

## 用户、角色与权限

用户、角色和权限用于表达管理授权和业务授权。

推荐流程：

1. 创建或导入用户。
2. 按职责分配角色。
3. 尽量把权限绑定到角色，而不是直接绑定到用户。
4. 需要时使用组织或租户分组用户。
5. 定期复核高权限账号。

安全事件处理中，建议先禁用用户，保留审计历史和绑定关系，再决定是否删除。

## 登录策略与 MFA

登录策略用于定义额外认证要求。

推荐基线：

- 管理员角色强制 MFA。
- 敏感应用开启应用级 MFA。
- 全局强制 MFA 前，先准备恢复流程。
- 登录失败和 MFA 失败需要联合审计。

ArmorAuth 支持 TOTP 和 Passkey/WebAuthn。Passkey 适合作为无密码登录方式，也适合在浏览器和设备支持时提供抗钓鱼 MFA。

## 身份源

ArmorAuth 支持 OAuth2/OIDC、SAML、LDAP/AD 等外部身份源。

启用身份源前：

1. 配置元数据、issuer、端点或目录连接参数。
2. 将外部属性映射到本地用户字段。
3. 确认已有用户的绑定策略。
4. 测试身份源配置。
5. 决定用户自动注册或中间页确认绑定。
6. 在托管登录页展示该身份源。

运营注意事项：

- 身份源密钥应通过配置或管理 API 写入，不要提交到源码。
- LDAP/AD 需要验证 bind 凭据、搜索 base、用户过滤器、组映射和 TLS 设置。
- SAML 证书轮换时间需要对操作员可见。

## 联合账号绑定

联合绑定把本地用户与外部身份连接起来。

以下场景建议复核绑定：

- 用户邮箱变更。
- 外部账号疑似被盗。
- 身份源更改 subject 标识格式。
- 用户需要解绑后重新绑定。

删除绑定不应自动删除本地用户，除非这是明确的账号生命周期操作。

## SCIM 同步

SCIM 端点用于外部系统同步用户和组。

运营建议：

- 为同步客户端使用专用凭据。
- 尽量限制网络访问。
- 监控同步错误。
- 停用用户时同步处理本地 session 和授权记录。
- 组到角色映射保持简单并形成文档。

## Webhook

Webhook 用于把事件投递到外部系统。

推荐实践：

- 使用 HTTPS 目标地址。
- 每个 endpoint 使用独立 secret。
- 接收方必须校验签名。
- 监控投递失败和重试。
- 接收方变更负责人时轮换 webhook secret。

## Actions

Actions 是自定义 Java 行为扩展点。

部署自定义 Action 前：

1. 审查实现的安全性和副作用。
2. 确认重复调用或重试时行为安全。
3. 验证失败路径。
4. 记录负责人和回滚步骤。

## Key 与 Secret 操作

ArmorAuth 会加密保存敏感数据，并把签名密钥存储在数据库中。

操作员职责：

- 接收真实用户前配置稳定加密 key。
- 在数据库外备份 crypto key。
- 将 `jwk_key` 表纳入数据库备份。
- 通过分阶段重加密流程轮换 crypto key。
- 与业务负责人协同轮换 OAuth client secret 和 webhook secret。

旧 key 对应的密文全部迁移前，不要移除旧 key。

## 审计与监控

建议定期查看：

- 登录成功和失败。
- MFA 挑战和失败。
- Token 签发与刷新模式。
- 管理 API 变更。
- 身份源变更。
- Webhook 投递失败。
- 授权检查拒绝。
- 数据库和迁移异常。

高风险变更应关联工单、操作人和时间。

## 备份与恢复演练

生产依赖备份前，应先做恢复演练。

最小演练流程：

1. 将近期数据库备份恢复到隔离环境。
2. 提供匹配的 crypto key 配置。
3. 使用恢复数据启动 ArmorAuth。
4. 确认用户、应用、JWK 和加密身份源密钥可读取。
5. 验证登录和 Token 签发流程。

## 事件处理

管理员账号疑似泄露：

1. 禁用账号或轮换凭据。
2. 复核近期审计事件。
3. 轮换受影响应用、身份源和 Webhook 密钥。
4. 必要时撤销可疑授权。
5. 删除记录前先保留证据。

签名密钥疑似泄露：

1. 如果泄露仍在发生，先停止接受外部流量。
2. 轮换 JWK。
3. 必要时撤销受影响 Token。
4. 确认依赖方刷新 JWKS。
5. 审查数据库和 crypto key 访问记录。

身份源密钥疑似泄露：

1. 在外部身份源侧轮换密钥。
2. 更新 ArmorAuth 配置。
3. 测试身份源登录。
4. 复核泄露窗口内的联合登录事件。
