# ArmorAuth 操作手册

本文描述 ArmorAuth 运行后的常见管理和运营流程，关注系统如何被日常使用，而不是本地 demo 脚本。

## 操作角色

| 角色 | 职责 |
| --- | --- |
| 平台管理员 | 部署、数据库、密钥、备份、监控 |
| 身份管理员 | 用户、组织、身份源、登录策略 |
| 应用管理员 | OAuth/OIDC 应用、Scope、Redirect URI、应用 MFA 策略 |
| 安全审计员 | 审计、Token 活动、Webhook 投递、策略验证 |

## 初始检查

首次部署后建议完成：

1. 确认公开 issuer URL 稳定且使用 HTTPS。
2. 替换开发管理员凭据。
3. 配置加密 key 和备份存储。
4. 确认 JWK 表已生成并纳入备份。
5. 检查默认应用、Scope、角色、权限和登录策略。
6. 确认管理操作会记录审计日志。

## 应用管理

应用代表 OAuth2/OIDC Client。

创建应用时需要确认：

- 为客户端类型选择正确的 grant type。
- 只登记可信 redirect URI。
- 浏览器和移动端客户端启用 PKCE。
- 只有能保护密钥的客户端才使用 confidential client 认证。
- Scope 控制在最小必要范围。
- 判断是否需要用户授权确认。
- 判断是否需要应用级 MFA。

运营注意事项：

- Client secret 只在创建或轮换时返回明文。
- 轮换 Client secret 需要与接入应用负责人协调。
- 调查或回滚可能发生时，优先禁用应用，而不是直接删除。

## 用户、角色与权限

用户、角色和权限用于表达管理授权和业务授权。

推荐流程：

1. 创建或导入用户。
2. 按职责分配角色。
3. 尽量把权限绑定到角色，而不是直接绑定到用户。
4. 需要时使用组织或租户分组用户。
5. 定期复核高权限账号。

安全事件处理中，建议先禁用用户，保留审计历史和绑定关系，再决定是否删除。

## 登录策略与 MFA

登录策略用于定义额外认证要求。

推荐基线：

- 管理员角色强制 MFA。
- 敏感应用开启应用级 MFA。
- 全局强制 MFA 前，先准备恢复流程。
- 登录失败和 MFA 失败需要联合审计。

ArmorAuth 支持 TOTP 和 Passkey/WebAuthn。Passkey 适合作为无密码登录方式，也适合在浏览器和设备支持时提供抗钓鱼 MFA。

## 身份源

ArmorAuth 支持 OAuth2/OIDC、SAML、LDAP/AD 等外部身份源。

启用身份源前：

1. 配置元数据、issuer、端点或目录连接参数。
2. 将外部属性映射到本地用户字段。
3. 确认已有用户的绑定策略。
4. 测试身份源配置。
5. 决定用户自动注册或中间页确认绑定。
6. 在托管登录页展示该身份源。

运营注意事项：

- 身份源密钥应通过配置或管理 API 写入，不要提交到源码。
- LDAP/AD 需要验证 bind 凭据、搜索 base、用户过滤器、组映射和 TLS 设置。
- SAML 证书轮换时间需要对操作员可见。

## 联合账号绑定

联合绑定把本地用户与外部身份连接起来。

以下场景建议复核绑定：

- 用户邮箱变更。
- 外部账号疑似被盗。
- 身份源更改 subject 标识格式。
- 用户需要解绑后重新绑定。

删除绑定不应自动删除本地用户，除非这是明确的账号生命周期操作。

## SCIM 同步

SCIM 端点用于外部系统同步用户和组。

运营建议：

- 为同步客户端使用专用凭据。
- 尽量限制网络访问。
- 监控同步错误。
- 停用用户时同步处理本地 session 和授权记录。
- 组到角色映射保持简单并形成文档。

## Webhook

Webhook 用于把事件投递到外部系统。

推荐实践：

- 使用 HTTPS 目标地址。
- 每个 endpoint 使用独立 secret。
- 接收方必须校验签名。
- 监控投递失败和重试。
- 接收方变更负责人时轮换 webhook secret。

## Actions

Actions 是自定义 Java 行为扩展点。

部署自定义 Action 前：

1. 审查实现的安全性和副作用。
2. 确认重复调用或重试时行为安全。
3. 验证失败路径。
4. 记录负责人和回滚步骤。

## Key 与 Secret 操作

ArmorAuth 会加密保存敏感数据，并把签名密钥存储在数据库中。

操作员职责：

- 接收真实用户前配置稳定加密 key。
- 在数据库外备份 crypto key。
- 将 `jwk_key` 表纳入数据库备份。
- 通过分阶段重加密流程轮换 crypto key。
- 与业务负责人协同轮换 OAuth client secret 和 webhook secret。

旧 key 对应的密文全部迁移前，不要移除旧 key。

## 审计与监控

建议定期查看：

- 登录成功和失败。
- MFA 挑战和失败。
- Token 签发与刷新模式。
- 管理 API 变更。
- 身份源变更。
- Webhook 投递失败。
- 授权检查拒绝。
- 数据库和迁移异常。

高风险变更应关联工单、操作人和时间。

## 备份与恢复演练

生产依赖备份前，应先做恢复演练。

最小演练流程：

1. 将近期数据库备份恢复到隔离环境。
2. 提供匹配的 crypto key 配置。
3. 使用恢复数据启动 ArmorAuth。
4. 确认用户、应用、JWK 和加密身份源密钥可读取。
5. 验证登录和 Token 签发流程。

## 事件处理

管理员账号疑似泄露：

1. 禁用账号或轮换凭据。
2. 复核近期审计事件。
3. 轮换受影响应用、身份源和 Webhook 密钥。
4. 必要时撤销可疑授权。
5. 删除记录前先保留证据。

签名密钥疑似泄露：

1. 如果泄露仍在发生，先停止接受外部流量。
2. 轮换 JWK。
3. 必要时撤销受影响 Token。
4. 确认依赖方刷新 JWKS。
5. 审查数据库和 crypto key 访问记录。

身份源密钥疑似泄露：

1. 在外部身份源侧轮换密钥。
2. 更新 ArmorAuth 配置。
3. 测试身份源登录。
4. 复核泄露窗口内的联合登录事件。
